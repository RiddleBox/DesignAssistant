## 一、Phase 3 定位

Phase 2 证明的是「链路能跑通」。Phase 3 要证明的是「链路能处理真实数据并支撑实际决策」。

**核心目标**：
> 以螺旋迭代方式，逐步将系统从「能运行的 MVP」推进到「处理真实信息、输出可信判断」的可演示状态。

**工程约定**：
- 不新建 3.1~3.5 实现文件夹，所有代码增量继续在 `phase2.1~2.5_implementation/` 中演进
- Phase 3 文档仅存放在 `phase3_plan/` 中
- 每轮迭代由 2.5 复盘驱动下一轮优先修复方向

### Iteration 5 — 建立可信质量基准 + 2.5 驱动修复闭环

**目标**：用外部未见样本重建质量数字，让 2.5 复盘基于可信数据驱动下一步修复方向

**状态**：⏳ 已推进到样本到位阶段（Batch 1 已完成范围导出，`incoming/` 已落地 560 条新样本，待分桶并进入 Batch 2）

**核心前提（Iter 4 复盘识别）**：

当前所有质量数字都有不同程度的水分：

| 指标 | 当前值 | 问题 |
|------|--------|------|
| 2.1 Precision | 95.2% | 测试集与 few-shot 样本高度重叠，不代表泛化能力 |
| 噪音抑制率 | noise_001~003 全抑制 | 仅 3 条噪音样本，样本量严重不足 |
| LLM 路径命中率 | 未测量 | api123.icu 随机 fallback，无法统计 |
| RAG 命中质量 | 未测量 | 命中条数有统计，但命中是否有效未评估 |

**当前优先级拆解（2026-04-13 收口）**：

#### A. 必做收口：决定 Phase 3 是否可信

1. **扩充外部测试样本**（最优先）
   - 优先通过现有样本收集模块 / openclaw 新批次，直接向 `background/real_intel_samples/incoming/` 补充 20+ 条 few-shot 未覆盖的真实外部样本（信号类 + 噪音类各约一半）
   - 噪音样本需覆盖多种噪音形态：财报套话、纯公告、非游戏行业、低信息量内容等
   - 手工构造仅作为补边界兜底，用于真实采集暂时缺失的极端噪音或临界样本

2. **重跑质量基准**
   - 在新样本集上重测 Precision / Recall / 噪音抑制率
   - 增补边界样本稳定性、弱信号保守性等观察指标
   - 建立可信的质量基线（"脱离 few-shot 的真实精度"）

3. **机会身份稳定性批跑验证**
   - 用真实稳定性批跑确认 `opportunity_key_stable` 是否持续为 `true`
   - 若仍出现重复机会，优先归因 key 生成规则，而非标题命名
   - 同时记录 `title_stable / opportunity_key_stable / posture_stable`，拆开身份问题与姿态问题

4. **API / provider 稳定性治理**
   - 补齐 timeout、provider、model、异常类型日志
   - 对比不同 provider / 中转路径，区分实现问题、环境问题与模型问题
   - 稳定后重跑同批样本，得到 LLM 路径真实命中率

5. **2.5 跨轮次归因**
   - 积累 10+ 次真实链路运行记录
   - 让 2.5 对比多次结果，识别持续性系统性问题 vs 偶发问题

6. **RAG 命中质量评估**
   - 62 条文档中 32 条 `content_type=background`，2.2 当前不请求此类型
   - RAG 实际有效文档只有 30/62，需要评估重分类后能否提升命中质量
   - 重点不是“命中几条”，而是“是否真的改善 2.2 / 2.3 输出”

#### B. 实用增强：决定输出是否真能拿去用

1. **弱信号/单信号场景的克制表达**
   - 单条信号时优先输出“观察 / 挂监控 / 补二跳证据”的保守建议
   - 避免在证据过薄时自动膨胀成完整行动方案

2. **姿态漂移解释能力**
   - 当 `title_stable=true` 但 `posture_stable=false` 时，显式说明是证据变化、2.1 抽取波动，还是 2.2 / 2.3 路径随机性导致

3. **报告决策摘要层**
   - 在报告前部增加更高密度的 why-it-matters / 建议动作 / 暂不建议动作摘要
   - 让报告从“结构完整”升级为“可直接讨论”

4. **fallback 可消费性**
   - 保留调试透明度，但降低“规则引擎生成，LLM 未跑通”对最终阅读体验的破坏性
   - 更清楚地区分“主结论可信度”与“链路是否降级”

| 批次 | 任务 | 主要产出物 | 验收口径 |

**Iteration 5 建议执行顺序**：
1. 先通过现有样本收集模块拉一批新样本，完成 **Batch 1**
2. 紧接着基于这批新样本做 **Batch 2**，解决“数字是否可信”
3. 再做 **Batch 3 + Batch 4**，解决“身份与运行是否稳定”
4. 最后做 **Batch 5 + Batch 6**，把复盘和实用化层补齐

**Iteration 5 最小验收标准**：
- 有一套与 few-shot 不重叠的外部样本基线
- `opportunity_key` 稳定性有真实批跑证据，而不是仅代码逻辑自证
- provider / timeout / fallback 有分层日志，可支持归因
- 2.5 能开始对多轮结果做聚合判断
- 报告在弱信号场景下不再默认输出过重建议

**Phase 3 评测框架总口径（2026-04-13 补充澄清）**：

**1. 先区分四类对象，不混用**
- `候选池`：例如 `batch1_bucket_candidates` / `batch2_bucket_candidates`，作用是从大量外部样本中筛出待处理对象，**不是 benchmark 真值**

- 外部新样本导入 → 候选分桶

- 在稳定运行条件下执行全量 benchmark
- 将其中一部分长期保留为固定回归基线，剩余继续作为扩展候选来源 [[memory:zhkz686l]]

**3. 对 `batch1` 的正确定位**

**Batch 2 质量基线评测口径（2026-04-13 新增）**：

**1. 评测目标**
- 目标不是追求单个漂亮数字，而是建立“外部未见样本下系统到底稳不稳”的可信基线
- 结果必须能区分真实能力、边界波动与运行环境噪音，避免把三者混在一起解读

**2. 样本集拆分口径**
- 主基线样本集：仅统计 Batch 1 中“真实采集主样本”，用于形成对外可信数字
- 边界观察样本集：单独统计 `boundary` 样本，用于观察误报、漏报与保守性，不直接混入主基线平均值
- 补边界样本集：若存在手工补样本，应单列，不与真实采集主样本混算

**3. 主指标（需要固定输出）**
- `Precision`：2.1 提取出的信号里，有多少是真正应提取的有效信号
- `Recall`：应提取的关键信号里，有多少被 2.1 实际提取到了
- `Noise Suppression Rate`：`noise` 样本中，被压制为 0 信号或仅输出明显低价值结果的比例
- `Boundary Stability`：同一批 `boundary` 样本在重复运行时，是否保持大致一致的提取倾向（保守 / 提取 / 不确定）

**4. 观察项（记录但不直接包装成“主成绩”）**
- 弱信号保守性：证据偏薄时，系统是否倾向保守而非硬提炼成强信号
- 信号密度：单样本平均提取信号数，用于识别是否出现“看什么都像有机会”的膨胀倾向
- 下游可消费性：`2.2 / 2.3` 是否能基于这批输出形成合理而不过载的判断与姿态
- 运行稳定性备注：同一批次中是否出现 provider 超时、fallback、解析异常等运行噪音

**5. 统计与汇报规则**

- 不允许把 `boundary` 与手工补样本直接混入主 Precision / Recall，避免数字被污染
- 若某次运行存在明显 provider/fallback 干扰，应保留该次结果，但需标注为“运行受扰”，不直接拿来下结论
- 若重复运行差异明显，优先记录“波动区间 + 原因备注”，而不是只取最好的一次

- 若能拿到更细日志，还应补充异常类型分布，如 read timeout / connect timeout / HTTP status / JSON parse error / stream truncation

**6. 结果判读规则**
- 若不同 provider 条件下都稳定失败，优先怀疑实现问题或公共代码路径问题，而不是单一 provider 问题
- 若仅某个 `base_url / route_type` 波动明显，而同 provider 其他路径稳定，优先归因为中转链路问题
- 若 `2.1` 经常挂起但 `2.2 / 2.3` 在 replay 或 record 下稳定，优先归因为上游调用稳定性，而不是下游逻辑问题
- 若请求成功率高但输出差异极大，应单列为“模型随机性 / 温度与提示敏感性”问题，不与纯失败率混算
- 若主要问题来自 timeout 配置过紧，应优先调参验证，不要过早下结论说 provider 不可用

**7. 输出与汇报规则**
- 主报告至少要拆成三层：可用性（能否跑完）、稳定性（重复跑是否波动）、输出质量影响（是否改变 2.2 / 2.3 / 2.5 结果）
- 不允许只报“哪个 provider 成功率更高”，必须同时说明其 fallback 情况、耗时特征与输出污染程度
- 对每个异常分布明显的 provider 条件，都要附一句“最可能原因”备注，明确更像实现、环境、中转还是 provider 本身问题
- 若当前阶段样本量较小，必须明确标注“本轮结论用于定位问题，不作为最终生产选型结论”

**8. Batch 4 完成定义**
- 已对至少一组主样本完成多条件 provider 对照，并能形成可复述的异常分布结论
- 已能把实现问题、运行环境问题、provider / route 问题初步拆开，而不是继续笼统归因成“随机不稳定”
- 已为后续 Batch 5 提供带标签的运行记录，使 2.5 可以对“问题是否与特定 provider 条件相关”做跨轮次观察
- 若某个 provider 条件明显更稳，已能说明其代价：耗时、成本或输出差异，而不是只看成功率

**9. Batch 4 输出格式要求**
- 至少包含：样本批次、对照条件表、每组运行次数、异常类型分布、成功率/耗时/fallback 统计、对下游输出的影响摘要
- 对结论优先写“哪一层受 provider 条件影响最大”，而不是只列原始数字
- 若结论仍不充分，应明确下一步补充的是更多样本、更多 provider 条件，还是更细的日志埋点

**Batch 5 2.5 跨轮次归因口径（2026-04-13 新增）**：

**1. 归因目标**
- 目标不是再做一次单轮复盘，而是把 Batch 2 / Batch 3 / Batch 4 沉淀下来的多轮结果聚合起来，回答“哪些问题是持续性的，哪些只是偶发扰动”
- 核心是让 `2.5` 不再只对单次运行给出发现，而是能识别问题是否跨轮次重复出现、是否集中在某类样本桶、是否与特定 provider 条件相关

**2. 输入记录范围**
- 默认聚合最近至少 10 次真实链路运行记录；若总运行次数不足，可先从 5 次起步，但必须明确标注为早期观察版
- 每次记录尽量包含完整链路：`2.1 / 2.2 / 2.3 / 2.5` 结果、稳定性观测、provider 条件、fallback 与异常日志
- 优先纳入真实运行；`record / replay` 结果可作为辅助对照，但必须单列，不能与真实运行混算

**3. 聚合主轴**
- 样本维度：同一批样本、同一类样本桶（`signal / noise / boundary`）、同一代表性主题
- 输出维度：`2.1` 提取质量、`2.2` 机会生成、`opportunity_key` 稳定性、`2.3` posture 稳定性、`2.5` findings 类型分布
- 运行维度：`provider / model / route / timeout`、fallback 情况、异常类型、耗时波动
- 结论维度：问题出现频次、连续出现次数、受影响样本范围、最可能归因层级

**4. 必做聚合问题**
- 同一类 `2.5 finding` 是否在多轮中反复出现，还是只在个别异常运行中出现
- `opportunity_key` 不稳定是否集中在特定样本桶、特定主题，还是全局性问题
- posture 漂移是否主要与 `2.1` 抽取变化相关，还是与 `2.2 / 2.3` 路径随机性更相关
- provider 异常是否与某类 finding 高频共现，例如 timeout 高发时是否更容易出现“证据不足 / fallback 污染”
- `noise / boundary` 样本是否长期推动同一类误报或过度建议，而不是偶发触发

**5. 必记聚合字段**
- 运行标识：运行时间、批次名、样本批次名、代码版本、provider 条件组
- 样本摘要：`signal / noise / boundary` 数量、主样本主题、是否含手工补边界样本
- 结果摘要：`2.1` 信号数、`2.2` 机会数、`2.3` posture 分布、`2.5` findings / priorities 数量
- 稳定性摘要：`title_stable`、`opportunity_key_stable`、`posture_stable`、机会数量是否波动
- 运行干扰摘要：fallback 次数、异常类型、超时情况、是否判定为“运行受扰”

**6. 判读规则**
- 同类问题连续出现 3 次及以上，且不依赖单一 provider 条件时，优先判定为持续性系统问题
- 某类问题只在“运行受扰”批次出现，优先标为偶发运行问题，不直接上升为能力退化结论
- 某类问题只集中在 `boundary` 样本，应判为边界能力议题，而不是主链路整体失效
- 某类问题在更换 provider / route 后明显消失，优先归因为运行条件相关，而不是 prompt 或逻辑本身突然变好
- 若同一问题在真实运行与 record / replay 对照中都存在，才更值得怀疑实现逻辑或模型能力问题

**7. Batch 5 输出结构**
- 第一层：趋势总览——本轮聚合覆盖多少次运行、多少类样本、有哪些高频问题
- 第二层：问题分层——持续性问题、偶发运行问题、边界能力问题分别列出
- 第三层：关联解释——哪些问题和 `provider / route / timeout` 有关，哪些和特定样本桶或主题有关
- 第四层：修复建议——下一轮优先修哪一层，以及为什么先修这一层最划算

**8. 完成定义**
- 已形成一版跨轮次聚合摘要，而不是零散单次报告堆积
- 已能明确指出至少 2~3 类问题分别属于持续性问题、偶发问题或边界问题
- 已能说明某类问题是否与特定 provider 条件或样本桶显著相关
- 已能把 Batch 5 结论反哺下一轮 Iteration 优先级，而不是停留在“发现很多问题”层面

**9. Batch 5 输出格式要求**
- 至少包含：聚合运行范围、主要高频问题、连续出现问题列表、偶发异常列表、按样本桶的影响摘要、按 provider 条件的关联摘要
- 对结论优先写“哪些问题值得进 backlog，哪些先不要过度处理”，而不是简单把所有现象平铺出来
- 若当前运行次数仍少，应明确写出“这是早期趋势观察，不是最终长期统计结论”

**Batch 6 实用化输出收口口径（2026-04-13 新增）**：

**1. 收口目标**
- 目标不是再增加更多结构化字段，而是让报告从“可调试产物”升级为“可直接拿去讨论和使用的产物”
- 核心是同时满足三件事：弱信号时足够克制、姿态变化时可解释、发生 fallback 时仍保持可消费而不误导

**2. 收口范围**
- 本批次重点覆盖 `2.2 / 2.3 / report_writer / 2.5` 的最终表达层，不要求先改动 2.1 主体提取逻辑
- 若某些表达问题本质上来自上游能力不足，可在 Batch 6 中标记并回流到前面批次，但 Batch 6 本身优先解决“如何正确表达当前能力边界”
- 输出层优化不应掩盖真实链路状态；调试透明度必须保留，只是从主叙事层移到更合适的位置

**2A. 职责边界与反越权护栏**
- Batch 6 只负责输出层收口，不负责重算 `2.1 / 2.2 / 2.3` 的核心判断
- `report_writer` 不得推翻 `2.2` 的机会判断，不得私自改写 `2.3` 的原始动作结论；可以补充前提、风险、执行条件与谨慎标签，但不能替上游重做决策
- 若输出层发现上游判断明显不合理，允许补充不确定性说明、执行前提与“建议回流上游修正”的标记，但不允许长期代偿上游缺陷
- 弱信号收口的本质是“保守呈现”，不是“输出层改判”；若 `2.3` 在弱信号下持续给出过重动作，应回流修复 `2.3`，而不是由 Batch 6 长期偷偷改写
- posture 漂移的根因归因以 `2.5` 的跨轮次结论为准；若当前证据不足，输出层只能写“可能原因 / 待归因”，不得把猜测包装成确定性裁决
- 当 `opportunity_key_stable=true` 但 `posture_stable=false` 时，必须优先表述为“同一机会下的姿态判断波动”，避免把姿态问题误写成身份裂变问题

**3. 必做收口主题**
- 弱信号 / 单信号场景的保守表达：证据薄、样本少、信号单一时，优先输出观察、补证据、挂监控，而不是直接膨胀成重行动方案
- 姿态漂移解释：当 `title_stable=true` 或 `opportunity_key_stable=true` 但 `posture_stable=false` 时，要明确写出最可能是证据变化、2.1 抽取波动、2.2 判断波动还是 2.3 行动设计波动
- 报告摘要层：在前部提供高密度的 why-it-matters、建议动作、暂不建议动作、关键不确定性摘要
- fallback 可消费性：让用户一眼区分“主结论是否仍可参考”与“链路是否降级运行”，避免把两者混成一句技术告警

**4. 弱信号表达规则**
- 当样本仅包含单条弱信号、单源转述或明显缺乏 corroboration 时，默认不直接输出高承诺 posture 或过满执行方案
- 默认优先级顺序为：补二跳证据 > 继续观察 > 小范围验证；除非有强 supporting evidence，否则不直接升级为大动作建议
- 对弱信号样本，报告里必须显式写出“当前更适合做什么”和“当前不建议直接做什么”
- 若系统仍给出较重姿态，应附一句原因说明，明确是因证据强度、时效性或上下文证据支持，而不是默认措辞惯性

**5. 姿态漂移解释规则**
- 对所有 `posture_stable=false` 的批次，至少输出一条“最可能来源”解释，优先级为：`2.1` 抽取变化 → `2.2` 机会判断变化 → `2.3` 行动设计变化 → provider / fallback 干扰
- 若 `opportunity_key_stable=true` 且 posture 漂移明显，应明确写为“同一机会下的姿态判断波动”，避免误读成机会身份裂变
- 若漂移与 provider 条件或 fallback 强相关，应在主摘要中标记“运行条件敏感”，而不是只埋在日志里
- 若暂时无法确定漂移来源，也应明确写为“待归因”，而不是给出过度确定的解释

**6. 报告摘要层结构**
- 报告前部建议固定为四块：`为什么值得关注`、`建议动作`、`暂不建议动作`、`关键不确定性`
- `为什么值得关注` 要面向决策价值，而不是复述原文事件
- `建议动作` 不超过 3 条，且优先给出低成本、可验证、可回退的动作
- `暂不建议动作` 必须出现于证据不足、姿态偏保守、或链路受扰场景，用于抑制默认乐观膨胀
- `关键不确定性` 要明确是信息缺口、判断分歧、还是运行受扰，不允许只写模糊的“仍需观察”

**7. fallback 表达规则**
- 保留 fallback 事实，但不要让“规则引擎生成，LLM 未跑通”直接占据主结论位置
- 主摘要先回答“当前结论还能不能参考、参考到什么程度”；技术降级信息放入单独的运行说明区
- 若 fallback 未显著改变主结论，可标记为“结论方向可参考，表达层为降级产物”
- 若 fallback 明显影响结论质量，则必须在摘要层提升告警级别，明确写出“本轮仅可作弱参考”

**8. Batch 6 验证方式**
- 选取至少 3 类样本做对照：强信号样本、弱信号 / 单信号样本、运行受扰样本
- 对每类样本至少抽取 2~3 份报告做人工检查，确认是否仍存在行动建议过满、漂移无解释、fallback 抢占主叙事等问题
- 若可能，结合 Batch 5 的高频问题列表优先验证最常见的误表达模式
- 验证结果应保留示例报告与人工点评，作为后续输出层回归基准 [[memory:zhkz686l]]

**9. Batch 6 完成定义**
- 弱信号样本的报告不再默认输出过重建议，而能稳定体现“观察 / 补证据 / 小范围验证”导向
- posture 漂移样本的报告已能给出至少一条像样的解释，而不是只告诉用户“结果不稳定”
- fallback 运行的报告已能区分“结论可信度”与“链路降级状态”，降低阅读污染
- 报告前部已具备可直接讨论的摘要层，而不是必须通读整份结构化报告才能抓到重点

**10. Batch 6 输出格式要求**
- 至少包含：对照样本类型、每类样本的表达变化、弱信号保护效果、姿态漂移解释效果、fallback 可消费性变化、仍待修项
- 对结果优先写“报告是否更适合真实讨论”，而不是只列新增了哪些字段
- 若存在 trade-off，应明确写出：例如可读性提升是否牺牲了部分调试直观性，以及如何平衡

| 风险项 | 严重度 | 状态 | 应对措施 |
