## 一、Phase 3 核心目标

> **用螺旋迭代方式，将系统从「能运行的 MVP」推进到「处理真实信息、输出可信判断」的可演示状态。**

最终验收标准（Iteration 3 完成时）：
- 系统能稳定处理 openclaw 每日采集的真实信息流
- 2.1 能从混合噪音的真实输入中可靠提取有价值信号
- 2.2/2.3 输出能支撑真实工作流中的方向判断
- 2.5 能持续识别质量问题并驱动下一轮修复

## 三、各模块 Phase 3 目标

### 2.1 情报解码模块

**Phase 3 目标**：在真实混合数据（信号+噪音）下稳定运行

**关键变化**：
- 输入从手工构造样本 → openclaw 真实采集内容
- 需要验证噪音抑制能力（noise_001~003 类型的内容应输出空信号或低置信）
- 按 Iteration 2 复盘结果定向优化 Prompt/few-shot

**当前版本**：v1.3（含 regulatory 信号类型，11个 few-shot 样例）

---

### 2.2 机会判断模块

**Phase 3 目标**：基于真实信号池输出可读的机会判断

**关键变化**：
- 信号来源从 M1-M6 固定样本 → 每日动态真实信号池
- opportunity_title 语义化已修复（v1.1）
- 需验证多源异质信号下的聚类稳定性

---

### 2.3 行动设计模块

**Phase 3 目标**：输出对真实机会判断有实际参考价值的行动方向

**关键变化**：
- 输入质量提升后，验证 2.3 输出是否随之改善
- 暂不做模块级改动，由 2.5 复盘决定是否需要调整

---

### 2.4 RAG 上下文模块

**Phase 3 目标（Iteration 3）**：obsidian 知识库内容入库，为 2.1/2.2 提供外部上下文

**关键决策**：
- `content_type` 替代 `use_as`（描述性而非指导性，消费权归下游）
- Iteration 1/2 不接入，避免干扰质量归因
- Iteration 3 开始联调，验证是否带来净增益

---

### 2.5 复盘模块

**Phase 3 目标**：作为螺旋迭代的核心引擎，每轮运行后驱动下一轮修复方向

**关键变化**：
- 从「单案例示例验证」→「批量真实案例持续复盘」
- Iter 4（2026-03-29）已升级为 LLM 深层归因（`llm_attributor.py`），能识别规则层发现不了的语义层问题
- 需要向跨轮次聚合归因演进：对比多次运行结果，识别持续性系统问题 vs 偶发问题
- 不做复杂观测平台，保持 MVP 归因结构

## 四、样本管道设计

### 4.1 文件夹约定

```
background/real_intel_samples/
  incoming/       ← openclaw 脚本定期投放（另一端维护）
  processed/      ← batch 脚本处理完后自动移入
  (根目录)        ← 手动整理的参考样本（sample_001~011, noise_001~003）
```

### 4.2 批量运行脚本设计（Iteration 1 主要产出）

**文件**：`data-layer/projects/proj_004/run_batch_real.py`

**职责**：
1. 扫描 `incoming/` 目录，读取所有 `.json` 文件
2. 逐条调用 2.1 decoder
3. 聚合所有有效信号（`signals` 非空）到信号池
4. 调用 2.2 → 2.3
5. 调用 2.5 复盘
6. 将已处理文件移入 `processed/`（无论有无信号，避免重复处理）
7. 输出本批次摘要：处理总数 / 有信号条数 / 噪音条数 / 信号池大小

**关于噪音持久化**：文件统一移入 `processed/`，2.5 复盘结果中记录哪些 source_id 触发了 0 信号。后续如需审计噪音分布，查复盘结果即可，不需要单独噪音文件夹。
