## 三、增强任务（联调稳定后）

### 增强A：Taxonomy 边界澄清（P1）

- **问题**：technical/market/team/capital 四类在边界案例上 Precision 不稳定
- **方案**：补充 2-3 个边界 few-shot 样例，明确排除规则
- **触发时机**：2.2 联调中发现因 taxonomy 模糊导致的评估错误

### 增强B：多信号聚合逻辑优化（P2）

- **问题**：同一事件多条信号时，去重/合并逻辑不稳定
- **方案**：在 decoder.py 后处理层加信号去重规则
- **触发时机**：端到端测试中出现重复信号干扰评估

### 增强C：Prompt → LLM 正式 API 接入（P1）

- **问题**：phase2.1 历史入口已存在多处独立配置，真实调用链路难以统一维护
- **方案**：统一迁移到项目级 `llm_config`，并清理旧入口
- **当前结果**：✅ 已完成统一接线，decoder 已读取统一配置；DeepSeek 请求可发出，当前重点已转为稳定性与耗时治理
- **后续待办**：
  1. 增加统一 timeout 配置，避免请求无限等待
  2. 增加更清晰的超时 / 连接失败日志
  3. 做一次 provider 对照验证，区分配置问题与环境问题
  4. 保留当前调试输出，待稳定后再决定是否收敛
  5. 增加阶段级耗时埋点：至少拆出 `screen_llm_ms / main_llm_ms / post_process_ms / validate_ms / total_ms`
  6. 评估 prompt 体积与输出 token 控制，确认是否可通过更短 prompt / 更小 `max_tokens` 降低主解码耗时
  7. 为批量真实样本增加并发批处理能力：多样本并行调用 API（受并发上限与速率限制约束），优先提升 wall-clock time，而非单请求 latency
  8. 为并发模式补齐限流、重试退避、失败样本隔离和结果汇总，避免高并发下整体批次失败
- **触发时机**：真实样本 baseline 初步跑通后立即进入治理

### 增强D：真实样本吞吐优化（P1）

- **问题**：单样本真实解码在 DeepSeek 下约 10~13s，串行批处理会显著拉长真实样本评测总时长
- **方案**：
  1. 保持单样本 decode 逻辑不变，先在 runner / batch 脚本层实现受控并发
  2. 并发单位以“样本”为主，而不是在单个样本内部并发拆分
  3. 初始并发建议从 2~4 开始，结合速率限制和失败率逐步调参
  4. 将并发优化定位为“吞吐优化”，不假设能减少 DeepSeek 单请求内部处理时间
- **验收目标**：在不明显拉高失败率和超时率的前提下，降低真实样本批评测的总 wall-clock time
- **触发时机**：baseline 跑通并确认质量可接受后启动

## 五、本轮补充记录（2026-04-02）

- `phase2.1` 的旧 LLM 入口已继续收口到统一 `llm_config`，避免 decoder / 测试脚本 / 批处理脚本各自维护配置。
- 当前验证结论是：**DeepSeek 从接线角度看可正确发起请求，但在现环境下 completion 响应存在挂起现象。**
- 因此，本轮建议是：**保留统一配置改动，不为挂起现象回滚代码；将问题转为后续稳定性诊断任务。**
- 后续优先处理顺序：统一超时 → 明确失败日志 → provider 对照测试 → 再判断是否需要进一步改造调用层。
